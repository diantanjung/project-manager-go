Dependency Injection

Dependency injection berarti dependency diberikan dari luar, bukan dibuat diam-diam di dalam object. Project ini memakai manual constructor injection, pendekatan yang sederhana dan idiomatik untuk ukuran project ini.

Tanpa DI

Contoh yang sebaiknya dihindari:

func NewService() *Service {
    db := openDatabaseFromEnv()
    store := postgres.New(db)
    return &Service{store: store}
}

Masalahnya: service jadi tahu cara membuka database, sulit dites, dan bergantung pada environment.

Dengan DI di project ini

Dependency dibuat di composition root, yaitu cmd/server/main.go:

db, err := postgres.Open(ctx, cfg.DatabaseURL)
if err != nil {
    return err
}

tokenManager := auth.TokenManager{
    AccessSecret:  []byte(cfg.JWTSecret),
    RefreshSecret: []byte(cfg.JWTRefreshSecret),
    AccessTTL:     cfg.JWTExpiresIn,
    RefreshTTL:    cfg.JWTRefreshExpiresIn,
}

svc := service.New(postgres.New(db), tokenManager)
router := httpapi.NewRouter(cfg, svc)

Composition root

Composition root adalah tempat semua dependency konkret disusun. Di project ini tempatnya run di cmd/server/main.go. Di sana boleh ada detail konkret seperti PostgreSQL, config, token manager, dan router.

Kenapa tidak pakai DI library?

Untuk project ini, manual DI masih terbaca. Dependency utamanya hanya config, database, token manager, service, dan router. Library seperti Wire, Fx, atau container generic berguna jika dependency graph sudah jauh lebih besar atau butuh lifecycle management kompleks.

Pendekatan Kapan cocok Tradeoff
Manual constructor injection Project kecil sampai menengah, graph masih jelas. Wiring manual bertambah saat service makin banyak.
google/wire Ingin compile-time DI dan tidak keberatan code generation. Perlu file provider dan generate code.
uber/fx Aplikasi besar dengan lifecycle hooks. Lebih banyak konsep dan reflection.

DI dan interface

DI menjadi kuat saat digabung dengan interface. service.New menerima Store, bukan *postgres.Store. Namun saat runtime, kita memberi postgres.New(db).

func New(store Store, tokens auth.TokenManager) *Service

DI dan testing

Pada test service, kita bisa memberi store palsu. Pada test HTTP, kita bisa memberi service dengan store palsu, lalu memanggil router tanpa database sungguhan.

Prinsip praktis: buat dependency konkret di pinggir aplikasi, lalu kirim ke layer tengah lewat constructor. Jangan membuka database atau membaca env dari dalam service.
